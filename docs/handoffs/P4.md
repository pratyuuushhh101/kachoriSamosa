# P4 handoff

## P4.1 — Validated image ingestion and extraction drafts

Status: P4.1 and P4.2 implementation and isolated checks complete on `codex/p4-extraction`.

### Delivered

- Added `backend/aarogyashield/extraction/` image sanitization, bounded extraction schemas, a Gemma API adapter, an explicitly labeled fixture provider, draft service, and `POST /api/extraction-drafts` router.
- Added P4 fake-backed tests and generated referral fixtures. The PNGs were drawn locally with synthetic text; provenance is in `fixtures/referrals/PROVENANCE.md`.
- Server-selected patient/encounter bindings are checked before provider work and rechecked in the patient-scoped write unit of work. The model schema rejects extra identity/authorization fields. Draft category defaults to `restricted`; draft creation does not publish chart content.
- The API call is outside the write transaction. Only validated structured output, a SHA-256 of the sanitized image, and minimal provider metadata are persisted. No image URL is produced.
- The in-memory limit admits five starts per session per minute and the provider adapter admits at most two calls per process. Run one worker for this MVP; the limiter is not distributed. Requests with a declared `Content-Length` above 6 MiB are rejected; the final app should also install an ASGI request-body cap before multipart parsing so chunked uploads are bounded.

`python3 -m compileall -q backend/aarogyashield/extraction backend/tests/p4` and `git diff --check` — passed.

No real provider call was made. Google’s current official Gemma Gemini API documentation lists `gemma-4-26b-a4b-it` and image input support: <https://ai.google.dev/gemma/docs/core/gemma_on_gemini_api>. Account-level model access remains unverified and requires `GEMINI_API_KEY`; P4.3 owns the opt-in live smoke check and evidence.

### Integration notes for P3

- Mount the router with the real session `current_actor`, CSRF dependency, settings, and P3 unit-of-work adapter. Keep provider I/O outside the transaction.

## P4.2 — Explicit human review and atomic chart publication

Status: implementation and fake-backed acceptance checks complete.

### Delivered

- Added `ConfirmRequest` and `ConfirmationResponse`, `confirm_draft`, and `POST /api/extraction-drafts/{id}/confirm`.
- Requires an admin reviewer and `human_reviewed=true`. Shareable `dental` and `safety_summary` categories require explicit category review and no unresolved fields; `restricted` remains available for uncertain drafts.
- Resolves only draft ownership metadata before entering a patient-scoped UOW, then rereads the draft and checks its encounter binding while locked.
- Inserts one resource containing only the approved summary and category, appends the confirmation audit event, and stores the reviewed payload/response on the draft in the same transaction. No consent state changes.
- Exact version plus canonical request retry returns the stored response with HTTP 200; changed payload or stale version returns 409. First confirmation returns HTTP 201.

### Verification

`PYTHONPATH=backend python3 -m pytest backend/tests/p4 -q` — 25 passed (fake provider and transactional fake UOW).

Coverage includes reviewer role, cross-patient/encounter mismatch, unresolved uncertainty, restricted publication, resource field allowlist, idempotent retry, changed retry conflict, and audit-failure rollback. The route test checks 201/200 and `Cache-Control: no-store`.

The real PostgreSQL adapter, unique `source_draft_id` constraint, audit implementation, and consent-gated dentist read remain P3/integration checks. P4.3 live-provider evidence is still outstanding.
